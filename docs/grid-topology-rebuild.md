### Why the feeder lines matter

The critical insight that drives this rebuild is that **feeder line geometries encode the destination substation** in their physical coordinates. A feeder line drawn from Substation A to Substation B has its endpoint coordinate landing within ~200m of Substation B's point. This gives us a **verifiable, non-name-based** method to resolve inter-substation links.

## The 6-Rule Pipeline

The rebuild engine processes rules in priority order. Earlier rules (geometry, codes) are preferred; later rules (name matching, nearest-hub) are fallbacks.

### Rule 1 — Feeder Line Geometry Resolution

**Method**: For every feeder line feature whose source `ss_code` belongs to a Chennai substation, extract the **last coordinate** of the line geometry. Find the nearest substation point to that coordinate. If it is within **0.5 km** and is a *different* substation, establish a verified link.

**Why it works**: TNEB GIS operators physically drew these lines on the map from source to destination. The endpoint IS the destination — no name parsing needed.

**Handles reversed lines**: Some lines are stored with coordinates in reverse direction (destination → source). The engine checks both the start and end coordinates and uses whichever endpoint lands closer to another substation.

| Metric | Value |
|---|---|
| Links resolved | 612 (53.4% of all links) |
| Name matching used | **None** |
| Provenance tag | `geometry_line_endpoint` |

### Rule 2 — Feeder Code Prefix Matching

**Method**: TNEB feeder codes follow a convention where the **first 4 digits** are the parent substation's `ss_code`. When a feeder's code prefix doesn't match its own substation's code, and that prefix corresponds to *another* known substation, it indicates a cross-substation tie.

**Example**: Feeder `942419` belongs to SS `9424` (Velacherry). The prefix `9424` matches Velacherry's code — this is a local feeder. But if a feeder with code `922619` were found under a different SS, the prefix `9226` (Tharamani) would indicate a tie back to Tharamani.

| Metric | Value |
|---|---|
| Links resolved | 116 (10.1% of all links) |
| Name matching used | **None** |
| Distance ceiling | 8.5 km |
| Provenance tag | `feeder_code_prefix` |

### Rule 3 — Co-located Switchyard Proximity

**Method**: Substations within **0.35 km** of each other are on the same physical campus (e.g., a 230kV switchyard and its companion 33/11kV distribution SS). These are linked as `colocated_stepdown` connections.

**Example**: `230/110KV THARAMANI SS` (code 9226) and `400/230-110 KV TARAMANI GIS SS` (code 9443) are 62 meters apart — they are the same compound.

| Metric | Value |
|---|---|
| Links resolved | 12 (1.0% of all links) |
| Name matching used | **None** |
| Provenance tag | `colocated_proximity` |

### Rule 4 — Name-based Incoming Feeder Fallback

**Method**: Each substation has up to 3 `in_fdr_n_*` free-text fields (e.g., `"RA Puram 110KV TO LUZ 33KV"`). When Rules 1–3 haven't already resolved the source substation, the engine parses the text to extract the source name and matches it against known substations.

**Why this is a fallback**: The `in_fdr_n_*` fields contain **no codes** — only free-text descriptions. TNEB's GIS schema does not store a source substation code in these fields.

**Safeguards against false positives**:

1. **Token-set matching** (not substring): The name `TRUSTPURAM` will never match `PORT TRUST` because their token sets `{TRUSTPURAM}` vs `{PORT, TRUST}` don't overlap.
2. **Alias normalization**: Handles known TNEB spelling variants (`THIRUVANMIYUR` ↔ `TIRUVANMIYUR`, `VELACHERY` ↔ `VELACHERRY`, etc.)
3. **Stopword filtering**: Generic words like `SS`, `GIS`, `SUBSTATION`, `KV`, `FEEDER`, `TO`, `FROM` are stripped before comparison.
4. **Generic landmark rejection**: Single-token names like `ROAD`, `NAGAR`, `PARK` cannot match on their own.
5. **Voltage hierarchy enforcement**: Source must be ≥ target voltage (power flows downhill).
6. **Distance ceilings**: ≤ 25 km for 230kV+, ≤ 16.5 km for subtransmission.
7. **Skip if already linked**: If Rules 1–3 already connected this pair, Rule 4 doesn't duplicate it.

| Metric | Value |
|---|---|
| Links resolved | 378 (33.0% of all links) |
| Skipped (already resolved) | 123 |
| Name matching used | **Yes** |
| Provenance tag | `name_fallback` |

### Rule 5 — AE Section Office Jurisdictions

**Method**: For each substation, find the nearest Section Office within **3.0 km** and attach it as a `campus_section` connection. These are non-electrical (administrative) links.

| Metric | Value |
|---|---|
| Links resolved | 268 |
| Provenance tag | N/A (type = `section`) |

### Rule 6 — Residual Topological Grounding

**Method**: Any substation with **zero substation-type connections** after Rules 1–5 is connected to its nearest upstream hub (≥ 110kV) within a distance ceiling.

**Why this exists**: Some rural/peri-urban substations (e.g., Thervoikandigai, Thandalam, NCTPS) have no incoming feeder text, no feeder lines in the GIS, and no nearby co-located switchyard. Without this rule they would be isolated nodes on the map.

| Metric | Value |
|---|---|
| Links resolved | 28 (2.4% of all links) |
| Isolated substations grounded | 14 |
| Distance ceilings | ≤ 18 km (bulk), ≤ 15 km (distribution) |
| Provenance tag | `nearest_hub_fallback` |

## Output Schema

The generated `chennai_tneb_grid.json` has this top-level structure:

```json
{
  "version": "3.0.0",
  "source": "TNEB GIS Authoritative Survey — Geometry-First Ground-Truth Engine v3",
  "counts": { "substations": 286, "sections": 352 },
  "substations": [ ... ],
  "sections": [ ... ]
}
```

Each substation object contains:

| Field | Type | Source |
|---|---|---|
| `code` | string | `ss_code` from GIS |
| `name` | string | `ss_name` from GIS |
| `cleanName` | string | Extracted landmark (voltage/SS suffixes stripped) |
| `voltage` | string | `volt_ratio` from GIS |
| `tier` | string | Derived: `bulk` / `subtransmission` / `distribution` |
| `lat`, `lng` | number | GIS coordinates |
| `feeders` | array | From `feeders_master_metadata.json` |
| `connections` | array | Built by the 6-rule pipeline |
| `powerTransformersCount` | number | `no_pr_tr` from GIS |
| `totalCapacityMva` | number | `tot_ca_mva` from GIS |
| `incomingFeedersCount` | number | `no_in_fdr` from GIS |
| `incomingFeederNames` | array | `in_fdr_n_1/2/3` from GIS |
| `elevationM`, `riskCategory`, `compositeRiskScore`, etc. | various | Preserved from prior enrichment |

Each connection object contains:

| Field | Type | Description |
|---|---|---|
| `id` | string | Target substation code (or `sec_XXXX` for sections) |
| `name` | string | Target name |
| `type` | string | `substation` or `section` |
| `relation` | string | `incoming_feeder`, `outgoing_feeder`, `colocated_stepdown`, `campus_section` |
| `label` | string | Human-readable description |
| `voltage` | string | Voltage of the tie |
| `tier` | string | Target's voltage tier |
| `distanceKm` | number | Haversine distance between the two endpoints |
| `method` | string | Provenance: how this link was resolved |

## Integrity Checks

The rebuild engine enforces these invariants before writing the output:

1. **Zero isolated nodes**: Every substation must have ≥ 1 substation-type connection. The script exits with code 1 if any are found.
2. **Distance audit**: All connections > 15 km are logged with their provenance method. Currently 16 such connections exist, all are `name_fallback` ties between EHV/transmission stations in the outer metro.
3. **Bidirectional consistency**: Every connection is added in both directions (A→B and B→A) with reciprocal relation labels.

## Known Limitations

1. **35% of links still use name matching**: The TNEB GIS `in_fdr_n_*` fields are free-text with no source codes. Until TNEB adds a `source_ss_code` field, name matching is the only way to resolve these.
2. **14 substations have no GIS-verified links**: These peri-urban/rural stations (Kaladipet, NCTPS, Tollgate, Devambedu, etc.) have null `in_fdr_n_*` fields and no feeder lines in the GIS. They are connected to their nearest upstream hub via Rule 6.
3. **Feeder line direction is inconsistent**: Some lines are drawn destination→source in the GIS. The engine handles this by checking both endpoints, but it means a small number of links are tagged `line_startpoint_reversed`.
